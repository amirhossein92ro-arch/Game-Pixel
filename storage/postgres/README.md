The PostgreSQL runtime driver is deliberately unavailable. `STORAGE_DRIVER=postgres` fails before opening storage; neither `DATABASE_URL` nor an existing file can select a driver automatically. No PostgreSQL package or server is needed for the current application.

The normalized rehearsal schema in `../migrations/sqlite/001_normalized.sql` is the entity/constraint design. A PostgreSQL migration should use the same stable text identifiers, normalize emails in application code, use `BIGINT` for integer money/counts, `JSONB` for extension/snapshot payloads and `TIMESTAMPTZ` for UTC instants. Retain the original timestamp representation in the portable record. Translate SQLite `json_valid` checks and WAL pragmas inside the new adapter; they do not belong in business services. Validate the actual PostgreSQL DDL in a disposable database before release.

Implement named domain operations matching `storage/sqlite/*.cjs`, plus repositories and an explicit async unit of work from `../contracts.d.ts`. Current transactions are synchronous and reject Promises. Do not hide asynchronous PostgreSQL work inside that contract. Convert and test service transaction callbacks explicitly before enabling the driver.

Use one bounded process-lifetime connection pool, initially small enough for the VPS (for example max 5 after measurement), connection acquisition/statement timeouts, and a transaction-scoped client returned in `finally`. Always bind values (`$1`, `$2`, …); only fixed adapter-owned identifiers may become SQL. Do not create a connection for each repository method. Readiness should execute a bounded `SELECT 1`, with no URL/host/user details in the HTTP response.

Future checkout must acquire product locks in sorted ID order, check active state and available stock, compute totals from trusted rows, conditionally decrement stock, write the order and immutable item snapshots, conditionally consume the coupon, and record the scoped idempotency result on the same client/transaction. Any failure rolls everything back. Unique idempotency/payment-reference constraints remain the final replay barrier. A real payment callback/event table belongs in the same transaction when an actual provider is implemented; today's provider is test-only and fails closed in production.

A PostgreSQL backup capability must run `pg_dump` against the explicitly configured database, verify the exit status and restore the result into an isolated database before treating it as a verified backup. Credentials belong in private environment/service configuration, never command-line logs or committed files. Existing SQLite backup/restore tools intentionally fail closed for unsupported runtime drivers. No `pg_dump` process is invoked by this repository today.

Use a separate migration role for DDL and an application role with only the required data access. Keep the port private, use strong rotated credentials, and verify server certificates with TLS for remote connections. Do not expose raw database errors, connection strings or SQL in HTTP responses. Add versioned, additive migrations first; validate code rollback compatibility separately from any database recovery procedure.
