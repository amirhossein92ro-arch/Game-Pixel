# داشبورد مشتری WEB 2

## اجرا

در ریشه پروژه با Node.js شاخه 24 (حداقل 24.15)، `npm ci` و `npm start` را اجرا کنید و `http://localhost:5000/profile.html` را باز کنید. صفحات و API از همان سرور سرو می‌شوند. Live Server یا backend قدیمی این داشبورد را اجرا نمی‌کند. برای پورت دیگر، `PORT` و `APP_ORIGIN` را هماهنگ کنید.

حساب مشتری به تنظیم سرویس خارجی نیاز ندارد. برای پشتیبانی و اعلان‌های Admin، `ADMIN_PASSWORD` را در `.env` تنظیم کنید و از `/admin-login` وارد حساب مدیریت جداگانه شوید. مقدار باید ۱۲ کاراکتر یا بیشتر و حداکثر ۷۲ بایت UTF-8 باشد. در Production، HTTPS و `NODE_ENV=production` الزامی هستند.

## قابلیت‌ها

- داشبورد با مشخصات حساب، آواتار، تاریخ عضویت، تعداد سفارش‌ها، Pending، Delivered، علاقه‌مندی‌ها و شمارنده اعلان نخوانده.
- ویرایش نام، نام خانوادگی، نام نمایشی، ایمیل، موبایل و انتخاب شش آواتار فروشگاه. تغییر ایمیل یا موبایل نیازمند رمز فعلی است. آپلود تصویر شخصی در این نسخه ارائه نشده است.
- فهرست سفارش‌ها و جزئیات، با وضعیت‌های Pending، Paid، Processing، Shipped، Delivered و Cancelled. سفارش تاریخی فاقد userId به حساب مشتری جدید نسبت داده نمی‌شود.
- دفترچه آدرس با حداکثر ۱۰ آدرس، ویرایش، حذف با تأیید و انتخاب پیش‌فرض. عنوان، نام گیرنده، موبایل، استان، شهر، نشانی و کد پستی اختیاری ۱۰ رقمی ذخیره می‌شوند. Checkout از آدرس ذخیره‌شده و پیش‌فرض استفاده می‌کند.
- قلب روی کارت و صفحه محصول، علاقه‌مندی جداگانه هر حساب (حداکثر ۲۰۰) و افزودن به سبد فعلی فروشگاه. محصول حذف‌شده/غیرفعال همچنان قابل حذف از علاقه‌مندی‌هاست.
- تغییر رمز با bcrypt؛ تأیید رمز فعلی، رمز جدید متفاوت، حداقل ۱۲ کاراکتر و حداکثر ۷۲ بایت UTF-8. همه نشست‌های قدیمی پایان می‌یابند و برای همین مرورگر نشست جدید ایجاد می‌شود. فهرست نشست‌ها فقط مرورگر، تاریخ، انقضا و نشان نشست فعلی را نمایش می‌دهد.
- اعلان هنگام ثبت سفارش، تغییر وضعیت، پاسخ/تغییر وضعیت تیکت، تغییر رمز یا ارسال پیام توسط Admin. هیچ اعلان یا تیکت نمایشی در دیتابیس واقعی ساخته نمی‌شود. مرکز اعلان ۱۰۰ مورد آخر را نشان می‌دهد و خواندن همه شامل موارد قدیمی‌تر هم می‌شود.
- تیکت با موضوع، دسته‌بندی و متن، پیام پیگیری، پاسخ مدیر و وضعیت‌های Open، Answered، Closed. مشتری نمی‌تواند در تیکت بسته پیام جدید بفرستد. Admin می‌تواند وضعیت را تغییر دهد و پاسخ ارسال کند.
- خروج نشست فعلی، پاک‌کردن نمایش و حافظه حساب و انتقال به صفحه ورود. داشبورد داده خصوصی را در localStorage ذخیره نمی‌کند. سبد و پیش‌نویس Checkout همان سازوکار موجود فروشگاه را دارند؛ رمز و توکن در آن‌ها قرار نمی‌گیرند.

بخش‌های متصل به سرور با دکمه به‌روزرسانی و هنگام بازگشت به پنجره تازه می‌شوند. صفحه قابل مشاهده هر ۶۰ ثانیه اطلاعات حساب را بررسی می‌کند؛ متن فرم در حال ویرایش را جایگزین نمی‌کند. برای فرم‌ها و دکمه‌های ارسال قفل درخواست و برای GETهای هم‌زمان یکسان اشتراک درخواست وجود دارد.

## قرارداد API

تمام مسیرهای مشتری به نشست معتبر کاربر و تمام مسیرهای Admin به نشست مدیریت جداگانه نیاز دارند. درخواست‌های تغییر‌دهنده JSON، مبدأ معتبر و CSRF نشست مناسب می‌خواهند. `userId` ارسال‌شده توسط مشتری برای تعیین مالکیت استفاده نمی‌شود. منابع متعلق به کاربر دیگر با 404 پاسخ می‌گیرند.

| روش | مسیر | رفتار |
|---|---|---|
| GET | `/api/account/dashboard` | user، stats و سه سفارش اخیر خود کاربر |
| GET / PUT | `/api/users/me` | مسیر موجود؛ توسعه برای firstName، lastName، displayName و avatar |
| GET / POST | `/api/users/me/addresses` | دریافت/افزودن آدرس |
| PUT / DELETE | `/api/users/me/addresses/:id` | ویرایش/حذف آدرس خود کاربر؛ PUT با isDefault برای پیش‌فرض |
| GET | `/api/users/me/wishlist` | productId، createdAt و product یا null برای محصول حذف‌شده |
| PUT / DELETE | `/api/users/me/wishlist/:id` | افزودن idempotent/حذف محصول برای همان حساب |
| PUT | `/api/users/me/password` | currentPassword، newPassword و confirmPassword؛ پاسخ csrfToken نشست جدید |
| GET | `/api/users/me/sessions` | نشست‌های غیرمنقضی بدون شناسه توکن، هش یا CSRF |
| GET | `/api/users/me/notifications` | items (حداکثر ۱۰۰) و unread واقعی |
| PUT | `/api/users/me/notifications/:id/read` | خواندن اعلان متعلق به حساب |
| PUT | `/api/users/me/notifications/read` | خواندن همه اعلان‌های همان حساب |
| GET / POST | `/api/tickets` | فهرست/ثبت تیکت؛ category از order، payment، product، account، other |
| GET | `/api/tickets/:id` | جزئیات و پیام‌های تیکت خود کاربر |
| POST | `/api/tickets/:id/messages` | ثبت پیام پیگیری در تیکت باز یا پاسخ‌داده‌شده |
| GET | `/api/admin/tickets` | فهرست تیکت‌ها همراه نام و ایمیل مشتری |
| GET / PUT | `/api/admin/tickets/:id` | جزئیات/تغییر status و ارسال message اختیاری |
| GET | `/api/admin/notification-recipients` | حساب‌های واقعی قابل انتخاب برای ارسال پیام |
| POST | `/api/admin/notifications` | userId، title، message؛ ثبت پیام فروشگاه در حساب مشتری |

مسیرهای موجود `/api/orders`، `/api/orders/:id`، `/api/admin/orders/:id` و `/api/auth/*` حفظ شده‌اند. تغییر وضعیت سفارش در همان تراکنش اعلان می‌سازد. درخواست تکراری Checkout با کلید idempotency، اعلان تکراری نمی‌سازد.

## دیتابیس و سازگاری

هنگام شروع سرور، جدول‌ها و ایندکس‌های جدید با CREATE IF NOT EXISTS به SQLite موجود اضافه می‌شوند؛ هیچ حساب، آدرس یا سفارش حذف نمی‌شود:

- `wishlist`: کلید مرکب user_id/product_id و تاریخ ذخیره.
- `tickets`: مالک، موضوع، دسته‌بندی، وضعیت و تاریخ‌ها.
- `ticket_messages`: پیام‌های مشتری/مدیر متصل به تیکت.
- `notifications`: مالک، نوع، عنوان، متن، منبع و تاریخ خواندن.
- `session_details`: اطلاعات غیرحساس مرورگر و تاریخ ایجاد، متصل به نشست با حذف وابسته.

فیلدهای پروفایل و آدرس‌های توسعه‌یافته در JSON حساب (`accounts.payload`) باقی می‌مانند و با مجموعه `users` هماهنگ می‌شوند. رمز هش‌شده فقط در `accounts.password_hash` قرار دارد. داده‌های قدیمی با فیلدهای کمتر قابل نمایش‌اند؛ هنگام ویرایش آدرس، کاربر فیلدهای جدید را تکمیل می‌کند. نشست‌های قدیمی بدون metadata هم کار می‌کنند.

## تست

`npm run check` و `npm test` را اجرا کنید. jsdom فقط وابستگی توسعه است. تست‌ها روی دیتابیس موقت اجرا می‌شوند و داده تست به `var/web2.sqlite` اضافه نمی‌کنند.

تست HTTP شامل دو کاربر، حساب مدیر، ذخیره/بازیابی داده پس از restart، کنترل مالکیت آدرس/سفارش/تیکت/اعلان، هش رمز، بستن نشست‌های قبلی، validation، CSRF موجود و ارتباط Admin با مشتری است. تست DOM فرم‌ها و رویدادهای واقعی frontend را به همان API واقعی وصل می‌کند: ثبت‌نام، ورود، داشبورد، ویرایش، آدرس، علاقه‌مندی، سبد، سفارش/جزئیات، تیکت/پاسخ مدیر، اعلان، تم، خروج و ورود مجدد. این تست DOM جای بررسی تصویری در مرورگر واقعی روی موبایل و تبلت را نمی‌گیرد.

SMS/ایمیل و push خارجی به این مرکز اعلان متصل نشده‌اند؛ اعلان‌ها درون فروشگاه‌اند. پرداخت همچنان همان PAYMENT_MODE=test موجود است و اتصال درگاه واقعی نیاز به توسعه Provider دارد.
